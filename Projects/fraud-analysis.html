01 tools used

Tools Used

The entire analysis was written and executed in MySQL across five SQL files: one data cleaning script and one per analytical question. No BI tool or spreadsheet layer was used. All aggregations, rate calculations, and comparisons run as pure SQL directly from the source tables.

MySQL Primary query engine. All cleaning, transformation, and analysis SQL was executed directly against the source database containing three tables: accounts, merchants, and transactions
Window Functions ROW_NUMBER() OVER(PARTITION BY ...) for duplicate detection across all 12 transaction columns simultaneously; SUM(COUNT(*)) OVER() for within-group percentage shares without a second table scan
CTEs (WITH clause) Used in Q3 and Q4 to stage intermediate results cleanly: fraud counts, repeat offender lists, legitimate averages, and channel totals each in their own named block, improving readability and auditability
Correlated Subqueries Used in Q3 and Q4 to compute per-account and per-merchant aggregates inside a SELECT list, allowing different filter conditions (is_fraud = 0 vs. is_fraud = 1) to appear as separate columns in the same output row
STR_TO_DATE / ALTER TABLE Used to convert the transaction_date column from plain text to a proper MySQL DATETIME type through a safe add-populate-verify-swap workflow that preserved the original column name
GROUP_CONCAT Collapses multi-row lists (fraud channels per account, accounts per merchant) into a single readable cell per group, making repeat-offender and merchant-exposure outputs human-readable without a separate pivot operation

03 data cleaning

Data Cleaning Process

The cleaning script addresses four concerns in order: duplicate detection, data standardisation (whitespace trimming across all three tables), date-column conversion from text to DATETIME, and NULL value auditing. All operations run directly against the source tables. Source file: fraud_analysis.sql

01
Check for Duplicates A subquery wraps the full transactions table and applies ROW_NUMBER() as a window function, partitioning across every column simultaneously. Any row whose assigned number exceeds 1 is a true duplicate. Selecting * on the outer query returns the full record for inspection before any deletion decision, giving the analyst visibility into which rows are affected.
SQL fraud_analysis.sql — Step 1 
SELECT *
FROM
  (SELECT *,
    ROW_NUMBER() OVER(PARTITION BY
      transaction_id, account_id, transaction_date,
      amount_ngn, merchant_id, merchant_name, merchant_category,
      transaction_channel, transaction_location,
      account_home_city, is_fraud, fraud_flag_reason
    ) AS r_num
  FROM transactions) AS Duplicates
WHERE r_num > 1;
02
Standardise Data — Trim Whitespace TRIM() is applied to every text column across all three tables in three separate UPDATE statements. Leading and trailing spaces cause silent mismatches in JOIN and GROUP BY operations: two values that look identical on screen fail to match when one carries an invisible space character. TRIM() resolves this across all tables before any analysis runs.
SQL fraud_analysis.sql — Step 2 
/* accounts table */
UPDATE accounts
SET
  account_id   = TRIM(account_id),
  city         = TRIM(city),
  account_type = TRIM(account_type),
  risk_profile = TRIM(risk_profile);

/* merchants table */
UPDATE merchants
SET
  merchant_id       = TRIM(merchant_id),
  merchant_name     = TRIM(merchant_name),
  merchant_category = TRIM(merchant_category),
  country           = TRIM(country);

/* transactions table */
UPDATE transactions
SET
  transaction_id       = TRIM(transaction_id),
  account_id           = TRIM(account_id),
  merchant_id          = TRIM(merchant_id),
  merchant_name        = TRIM(merchant_name),
  merchant_category    = TRIM(merchant_category),
  transaction_channel  = TRIM(transaction_channel),
  transaction_location = TRIM(transaction_location),
  account_home_city    = TRIM(account_home_city),
  fraud_flag_reason    = TRIM(fraud_flag_reason);
03
Convert Date Column from Text to DATETIME transaction_date was stored as a plain text string. The script converts it through a safe four-step workflow: inspect for format inconsistencies using HAVING COUNT(*) = 1 to surface dates appearing only once; add a new DATETIME column; populate it with STR_TO_DATE; verify no parse failures (STR_TO_DATE returns NULL on mismatch); then drop the original and rename the typed replacement. This preserves the original column name, keeping all downstream queries compatible.
SQL fraud_analysis.sql — Step 3 
/* 3a — Inspect date values for format inconsistencies */
SELECT transaction_date, COUNT(*) AS occurences
FROM transactions
GROUP BY transaction_date
HAVING COUNT(*) = 1
ORDER BY transaction_date;

/* 3b — Add and populate the new DATETIME column */
ALTER TABLE transactions
  ADD COLUMN txn_date DATETIME;

UPDATE transactions
SET txn_date = STR_TO_DATE(transaction_date, '%Y-%m-%d %H:%i:%s');

/* 3c — Check for parse failures (NULL = format mismatch) */
SELECT transaction_id, txn_date
FROM transactions
WHERE txn_date IS NULL;

/* 3d — Swap: drop original text column, rename typed replacement */
ALTER TABLE transactions DROP COLUMN transaction_date;
ALTER TABLE transactions RENAME COLUMN txn_date TO transaction_date;
04
Audit NULL Values Across All Tables Three SELECT queries run a full NULL count on every column across each table. Each column gets its own CASE WHEN expression so the audit arrives as a single summary row, covering all columns in one pass. SUM(CASE WHEN ... IS NULL THEN 1 ELSE 0 END) converts each NULL check to a binary integer per row, then sums across all rows — faster to read than running one query per column.
SQL fraud_analysis.sql — Step 4 
/* accounts table */
SELECT
  SUM(CASE WHEN account_id          IS NULL THEN 1 ELSE 0 END) AS null_id,
  SUM(CASE WHEN age                 IS NULL THEN 1 ELSE 0 END) AS null_age,
  SUM(CASE WHEN city                IS NULL THEN 1 ELSE 0 END) AS null_city,
  SUM(CASE WHEN account_type        IS NULL THEN 1 ELSE 0 END) AS null_acc_type,
  SUM(CASE WHEN avg_monthly_balance IS NULL THEN 1 ELSE 0 END) AS null_bal,
  SUM(CASE WHEN risk_profile        IS NULL THEN 1 ELSE 0 END) AS null_risk_profile
FROM accounts;

/* merchants table */
SELECT
  SUM(CASE WHEN merchant_id       IS NULL THEN 1 ELSE 0 END) AS null_id,
  SUM(CASE WHEN merchant_name     IS NULL THEN 1 ELSE 0 END) AS null_name,
  SUM(CASE WHEN merchant_category IS NULL THEN 1 ELSE 0 END) AS null_category,
  SUM(CASE WHEN is_registered     IS NULL THEN 1 ELSE 0 END) AS null_register,
  SUM(CASE WHEN country           IS NULL THEN 1 ELSE 0 END) AS null_country
FROM merchants;

/* transactions table */
SELECT
  SUM(CASE WHEN transaction_id       IS NULL THEN 1 ELSE 0 END) AS null_id,
  SUM(CASE WHEN account_id           IS NULL THEN 1 ELSE 0 END) AS null_acc_id,
  SUM(CASE WHEN merchant_id          IS NULL THEN 1 ELSE 0 END) AS null_merch_id,
  SUM(CASE WHEN merchant_name        IS NULL THEN 1 ELSE 0 END) AS null_name,
  SUM(CASE WHEN merchant_category    IS NULL THEN 1 ELSE 0 END) AS null_category,
  SUM(CASE WHEN transaction_channel  IS NULL THEN 1 ELSE 0 END) AS null_channel,
  SUM(CASE WHEN transaction_location IS NULL THEN 1 ELSE 0 END) AS null_location,
  SUM(CASE WHEN account_home_city    IS NULL THEN 1 ELSE 0 END) AS null_home,
  SUM(CASE WHEN is_fraud             IS NULL THEN 1 ELSE 0 END) AS null_fraud,
  SUM(CASE WHEN fraud_flag_reason    IS NULL THEN 1 ELSE 0 END) AS null_reason,
  SUM(CASE WHEN transaction_date     IS NULL THEN 1 ELSE 0 END) AS null_date
FROM transactions;

04 metrics per question

Metrics Used Per Question & Why

Every metric was chosen to answer a specific sub-question precisely. The most important recurring choice is using rate rather than raw count when comparing segments of different sizes. A segment with 500 transactions and 50 fraud events has the same 10% rate as one with 50 transactions and 5 events, but their raw counts look 10x different. Rate-based comparison is the only fair basis across unequal segment sizes.

Q1 Fraud Rate by Account Segment, Risk Profile & Channel
Fraud rate 100 * SUM(CASE WHEN is_fraud=1 THEN 1 ELSE 0 END) / COUNT(*). Normalises fraud occurrence to segment size, making Savings, Current, and Salary accounts directly comparable regardless of how many customers each type holds. Raw fraud counts would make larger segments appear riskier by default.
Total transaction value ROUND(SUM(amount_ngn), 2). Establishes the full monetary base of each segment or channel. Serves as the denominator for the fraud value share percentage, grounding rate comparisons in real naira amounts rather than transaction counts alone.
Fraud transaction value SUM(amount_ngn) WHERE is_fraud = 1 via correlated subquery. Isolates monetary value flowing through confirmed fraud cases only, calculated separately from the main aggregate so the filter condition can differ from the outer query's context.
Fraud value share (%) 100 * fraud_value / total_value. Converts transaction volume into monetary exposure per segment. A segment with a moderate fraud rate but high-value transactions loses more money than a high-rate, low-value one. This metric surfaces that difference and is the most financially consequential number in Q1.
SQL fraud_analysis_question1.sql 
/* Referential integrity check before joining */
SELECT
  a.account_id AS accts_id,
  t.account_id AS txns_id
FROM accounts a
  JOIN transactions t ON a.account_id = t.account_id
WHERE t.account_id NOT IN (SELECT a.account_id FROM accounts)
   OR a.account_id NOT IN (SELECT t.account_id FROM transactions);

/* Fraud rate by account type */
SELECT account_type,
  ROUND(100 * SUM(CASE WHEN is_fraud = 1 THEN 1 ELSE 0 END) / COUNT(*), 2) AS fraud_rate
FROM accounts a
  JOIN transactions t ON a.account_id = t.account_id
GROUP BY account_type
ORDER BY fraud_rate DESC;

/* Fraud rate by risk profile */
SELECT risk_profile,
  ROUND(100 * SUM(CASE WHEN is_fraud = 1 THEN 1 ELSE 0 END) / COUNT(*), 2) AS fraud_rate
FROM accounts a
  JOIN transactions t ON a.account_id = t.account_id
GROUP BY risk_profile
ORDER BY fraud_rate DESC;

/* Fraud rate by transaction channel */
SELECT transaction_channel,
  ROUND(100 * SUM(CASE WHEN is_fraud = 1 THEN 1 ELSE 0 END) / COUNT(*), 2) AS fraud_rate
FROM accounts a
  JOIN transactions t ON a.account_id = t.account_id
GROUP BY transaction_channel
ORDER BY fraud_rate DESC;

/* Fraud value as % of total transaction value */
SELECT
  ROUND((100 * (SELECT ROUND(SUM(amount_ngn), 2)
                 FROM transactions WHERE is_fraud = 1))
    / ROUND(SUM(amount_ngn), 2), 2) AS Fraud_txns_val_pct
FROM transactions;

/* Fraud value share by channel */
SELECT transaction_channel,
  CONCAT(ROUND((100 * (SELECT ROUND(SUM(amount_ngn), 2)
                       FROM transactions WHERE is_fraud = 1))
    / ROUND(SUM(amount_ngn), 2), 2), '%') AS Fraud_txns_vol_pct
FROM accounts a
  JOIN transactions t ON a.account_id = t.account_id
GROUP BY transaction_channel
ORDER BY Fraud_txns_vol_pct DESC;
Q2 Fraud Pattern Breakdown
Fraud count COUNT(*) per fraud pattern. Raw frequency showing which attack method appears most often in the flagged population. The primary ranking dimension for the fraud team to decide where to tighten detection rules first.
% of all fraud COUNT(*) / SUM(COUNT(*)) OVER() * 100. A window function computes the grand total in the same GROUP BY pass, giving each pattern's share without a subquery or second table scan. More efficient and less error-prone than a correlated subquery on a filtered dataset.
Total transacted SUM(amount_ngn) per fraud type. Total monetary exposure per pattern. High-value, low-count patterns are invisible on a frequency-only view; this column surfaces them alongside count for a complete picture.
Avg amount per transaction AVG(amount_ngn) per fraud type. Typical transaction size. A high average signals larger single-incident losses and directly guides where to set monetary alert thresholds in detection rules.
Max / Min amount MAX(amount_ngn) and MIN(amount_ngn). Reveals range and outliers within each pattern. A large gap between max and min signals one fraud type covers a wide spread of sizes, meaning a single fixed threshold would produce false positives at the low end or miss events at the high end.
SQL fraud_analysis_question2.sql 
/* Transaction count and amounts by fraud type */
SELECT
  fraud_flag_reason,
  COUNT(*) AS Fraud_count,
  CONCAT(ROUND(COUNT(*) / SUM(COUNT(*)) OVER() * 100, 2), '%') AS pct_of_all_fraud,
  ROUND(SUM(amount_ngn), 2)  AS total_transacted,
  ROUND(AVG(amount_ngn), 2)  AS avg_amt_per_txn,
  ROUND(MAX(amount_ngn), 2)  AS maximum_amt_per_fraud_type,
  ROUND(MIN(amount_ngn), 2)  AS minimum_amt_per_fraud_type
FROM transactions
WHERE is_fraud = 1
GROUP BY fraud_flag_reason
ORDER BY Fraud_count DESC;
Q3 High-Risk / Repeat Offender Accounts
Total fraud transactions COUNT(*) WHERE is_fraud = 1 GROUP BY account_id. Counts fraud events per account. The filter Total_fraud_txns > 1 in the repeat_offenders CTE defines the watchlist threshold: two or more events signal either an unresolved breach or a deliberate bad actor.
Avg legitimate amount AVG(amount_ngn) WHERE is_fraud = 0 per repeat-offender account. Establishes the normal spending baseline. Serves as the denominator in the ratio and as the reference point for fraud transaction sizes. Restricting to is_fraud = 0 ensures the baseline reflects only genuine account behaviour.
Avg fraud amount Correlated subquery: AVG(amount_ngn) WHERE is_fraud = 1 per account. Computed separately from the legitimate average using a correlated subquery, so both values can appear in the same output row despite requiring opposite filter conditions.
Fraud-to-legit ratio avg_fraud_amt / NULLIF(avg_legit_amt, 0). A ratio above 1.0 means fraud transactions are larger than the account's own normal spending: the primary indicator of external account takeover rather than owner misconduct. NULLIF prevents a division-by-zero error where an account has no legitimate transaction history.
Channels used GROUP_CONCAT(DISTINCT channel ORDER BY channel SEPARATOR ', '). Collapses the full fraud channel list into one readable cell per account. DISTINCT removes repetitions when the same channel was used in multiple fraud events on the same account.
SQL fraud_analysis_question3.sql 
WITH fraud_count AS (
  SELECT account_id, COUNT(*) AS Total_fraud_txns
  FROM transactions
  WHERE is_fraud = 1
  GROUP BY account_id
),
repeat_offenders AS (
  SELECT account_id, Total_fraud_txns
  FROM fraud_count
  WHERE Total_fraud_txns > 1
),
avg_legit_txn_amt AS (
  SELECT t.account_id,
    ROUND(AVG(t.amount_ngn), 2) AS avg_legit_amt
  FROM transactions t
    JOIN repeat_offenders ro ON t.account_id = ro.account_id
  WHERE is_fraud = 0
  GROUP BY account_id
),
channels_used AS (
  SELECT t.account_id,
    GROUP_CONCAT(DISTINCT t.transaction_channel
      ORDER BY t.transaction_channel SEPARATOR ', ') AS channels
  FROM transactions t
    JOIN repeat_offenders ro ON t.account_id = ro.account_id
  WHERE is_fraud = 1
  GROUP BY account_id
)
SELECT
  ro.account_id, a.account_type, a.risk_profile,
  ro.Total_fraud_txns, cu.channels, al.avg_legit_amt,
  ROUND((SELECT AVG(amount_ngn) FROM transactions t
    WHERE t.account_id = ro.account_id AND is_fraud = 1), 2) AS avg_fraud_txn_amt,
  ROUND((SELECT AVG(amount_ngn) FROM transactions t
    WHERE t.account_id = ro.account_id AND is_fraud = 1)
    / NULLIF(al.avg_legit_amt, 0), 2) AS Fraud_to_legit_ratio
FROM repeat_offenders ro
  JOIN accounts a           ON ro.account_id = a.account_id
  JOIN avg_legit_txn_amt al ON ro.account_id = al.account_id
  JOIN channels_used cu     ON ro.account_id = cu.account_id
ORDER BY Total_fraud_txns;
Q4 Merchant & Channel Exposure
Channel fraud % 100 * Fraud_amt / Total_amt per channel. Two separate CTEs compute total and fraud channel amounts independently, then join. This allows different WHERE conditions per CTE without a single large conditional aggregation that is harder to audit or maintain.
Merchant accounts GROUP_CONCAT(DISTINCT account_id ORDER BY account_id SEPARATOR ', '). Lists every account that transacted fraudulently at this merchant. Reveals whether fraud comes from one bad actor or spans multiple customers, distinguishing a single-account compromise from a merchant-level scheme.
No. of accounts COUNT(DISTINCT account_id). A higher count means fraud at this merchant affects a broader share of the customer base. Used as the primary ORDER BY key to surface the widest-impact merchants first rather than the highest-value ones.
Fraud composition % 100 * Fraud_amt / Total_amt per merchant via correlated subqueries. Primary merchant risk signal. A value near 100% means the merchant processes almost no legitimate transactions and should be blocked outright. Correlated subqueries allow total and fraud amounts to share different WHERE conditions in the same SELECT list.
SQL fraud_analysis_question4.sql 
/* Channel exposure */
WITH total_amt_per_channel AS (
  SELECT transaction_channel,
    ROUND(SUM(amount_ngn), 2) AS Total_amt
  FROM transactions
  GROUP BY transaction_channel
),
fraud_amt_per_channel AS (
  SELECT transaction_channel,
    ROUND(SUM(amount_ngn), 2) AS Fraud_amt
  FROM transactions
  WHERE is_fraud = 1
  GROUP BY transaction_channel
)
SELECT
  tc.transaction_channel,
  tc.Total_amt,
  fc.Fraud_amt,
  ROUND(100 * fc.Fraud_amt / tc.Total_amt, 2) AS Fraud_pct
FROM total_amt_per_channel tc
  JOIN fraud_amt_per_channel fc
    ON tc.transaction_channel = fc.transaction_channel;

/* Merchant exposure */
SELECT
  m.merchant_name, m.merchant_id, m.is_registered,
  GROUP_CONCAT(DISTINCT t.account_id
    ORDER BY t.account_id SEPARATOR ', ') AS merchant_accounts,
  GROUP_CONCAT(DISTINCT t.transaction_channel
    ORDER BY t.transaction_channel SEPARATOR ', ') AS Channels_Used,
  COUNT(DISTINCT t.account_id)  AS No_of_accts,
  ROUND((SELECT SUM(t.amount_ngn) FROM transactions t
    WHERE t.merchant_id = m.merchant_id), 2) AS Total_amt,
  ROUND((SELECT SUM(t.amount_ngn) FROM transactions t
    WHERE t.merchant_id = m.merchant_id AND is_fraud = 1), 2) AS Fraud_amt,
  ROUND((100 *
    (SELECT SUM(t.amount_ngn) FROM transactions t
      WHERE t.merchant_id = m.merchant_id AND is_fraud = 1) /
    (SELECT SUM(t.amount_ngn) FROM transactions t
      WHERE t.merchant_id = m.merchant_id)), 2) AS Pct_Fraud_comp
FROM transactions t
  JOIN merchants m ON t.merchant_id  = m.merchant_id
  JOIN accounts a  ON t.account_id   = a.account_id
WHERE t.is_fraud = 1
GROUP BY m.merchant_name, m.merchant_id, m.is_registered
ORDER BY No_of_accts DESC;

05 insights

Insights Per Question

Q1 — Fraud Rate by Account Segment, Risk Profile & Channel

Highest Rate by Account Type
Current Accounts
Current accounts carry the highest fraud rate. Higher transfer limits make them more attractive targets for large fraudulent transactions than Savings or Salary accounts.
Risk Profile Finding
High Risk leads; Medium does most damage
High-risk accounts record the highest per-segment fraud rate, confirming the bank's classification has some predictive power. But Medium-risk accounts generate more total fraud cases simply because that segment is significantly larger.
Most Dangerous Channels
Web & Mobile App
Web and Mobile App post the highest fraud rates among all channels, confirming digital card-not-present transactions as the primary attack surface across the portfolio.
Value vs. Count
Value share exceeds count share
Fraud's share of total transaction value exceeds its share of transaction count. Fraudulent transactions are on average larger than legitimate ones, making the financial damage disproportionate to the number of cases.
→

Current account holders lose more money to fraud because fraudsters target accounts where transfers can be larger. The bank's risk labels work to a point: high-risk customers do get hit more often. But medium-risk customers cause the most damage in total simply because there are far more of them. The fraud value share is the most important output of Q1: each fraudulent transaction takes more money than a typical legitimate one, so the financial damage is disproportionate to the case count.

Q2 — Fraud Pattern Breakdown

Most Frequent Pattern
Geographic Anomaly
Geographic anomaly is the most frequent fraud pattern, appearing in the largest share of all flagged transactions. Location-based attacks are the dominant method: a card used in a city or country the account holder has never visited.
Highest Value per Incident
Round-Amount Structuring
Round-amount structuring carries the highest average and maximum transaction values. The costliest type per incident even if it ranks lower by count: large, exact-figure transfers moved in single transactions.
Lowest Avg Amount
Velocity Spike
Velocity spike transactions are frequent but carry the lowest average amounts, consistent with fraudsters keeping individual transactions small to avoid auto-blocking rules based on single-transaction thresholds.
Timing-Based Pattern
Odd-Hour Large Transactions
Odd-hour large transactions (1am to 4am) combine a moderate count with high individual amounts, producing significant total exposure. Account holders are unlikely to notice an alert during these hours.

Q3 — High-Risk / Repeat Offender Accounts

Key Signal
Fraud-to-legit ratio > 1.0
The Fraud_to_legit_ratio exceeds 1.0 for most repeat offenders, meaning fraudulent transactions are consistently larger than the account holder's normal spending baseline. This is the strongest indicator of external account takeover.
Primary Breach Channel
Web & Mobile App
Web and Mobile App dominate the channels column for repeat offenders. POS and ATM appearances are minimal, placing digital channels as the primary surface through which compromised accounts continue to be exploited.
Risk Model Gap
Low/Medium labels on repeat offenders
Several repeat offenders carry Low or Medium risk profile labels in the accounts table. The bank's scoring model failed to identify these accounts as vulnerable before fraud events accumulated, a serious monitoring gap.
Interpretation
Account takeover, not owner fraud
When the same account appears repeatedly with fraud amounts exceeding the owner's legitimate spending baseline, it signals stolen credentials and a returning attacker: account takeover, not the account owner committing fraud.

Q4 — Merchant & Channel Exposure

Highest Risk Merchants
Unregistered (is_registered = 0)
Unregistered merchants record fraud compositions approaching or reaching 100%, meaning essentially every transaction through them is fraudulent. The bank already holds the is_registered flag and can block these destinations with zero false-positive risk.
Highest Monetary Risk
Crypto & Wire Transfer Merchants
Crypto exchanges and wire transfer merchants carry the highest Fraud_amt values despite lower transaction counts, making them the largest monetary risk per merchant: large amounts in few transactions.
Riskiest Channel
Web Channel
The Web channel posts the highest Fraud_pct among all channels, confirming it as the primary digital attack surface across the entire transaction portfolio, consistent with Q1 and Q3 findings.
Fraud Concentration
Narrow merchant subset
High-volume everyday merchants such as grocery stores and utility providers carry near-zero fraud composition. Fraud concentrates in a narrow subset of the merchant base: blocking a handful of categories addresses the majority of fraud without disrupting typical customers.

06 recommendations

Recommendations

Three recommendations follow, ordered from minimum viable to highest impact. Each is grounded directly in a finding from the four analytical questions.

// action items · ranked by impact
  • 01 Add OTP confirmation for round-amount transfers above 200,000 NGN
    Q2 shows round-amount structuring carries the highest average and maximum transaction values among all fraud patterns. Requiring a one-time password for any transfer where the amount is an exact multiple of 100,000 NGN adds one friction step that the vast majority of legitimate customers will never encounter. It targets the highest-value fraud type directly and costs little to implement through the existing authentication layer. Limitation: it addresses only one pattern and does nothing about geographic anomalies or odd-hour attacks, leaving most fraud volume untouched.
  • 02 Block unregistered merchants and activate geo-velocity rules
    Q4 shows unregistered merchants (is_registered = 0) process fraud at rates approaching 100%. The bank already holds this data and can block these destinations outright with zero false-positive risk to legitimate customers. Alongside this, Q2 ranks geographic anomaly as the single most common fraud pattern. A geo-velocity rule flags any transaction where the current location is physically impossible to reach from the previous location within the elapsed time between them. Both controls are rule-based, require no machine learning, and deploy through the existing transaction monitoring system. Together they address the two highest-frequency fraud patterns identified in the analysis.
  • 03 Freeze repeat-offender accounts, force re-KYC, and recalibrate risk scoring
    Q3 produces a concrete watchlist of accounts with more than one fraud event and Fraud_to_legit_ratios above 1.0. These accounts need outbound transfers suspended immediately. Affected customers should be contacted directly, passwords reset, and re-KYC completed before access is restored. Beyond the immediate account actions, Q3 reveals that several repeat-offender accounts carried Low or Medium risk labels when fraud occurred. The scoring model failed to predict their vulnerability. The fraud team should feed the characteristics of these accounts back into the scoring criteria: transaction velocity, channel mix, geographic spread, and average amounts relative to balance. This recommendation addresses the root cause. The first two block specific fraud routes; this one closes the monitoring gap that allowed repeat fraud to accumulate undetected.
