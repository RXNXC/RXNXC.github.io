01 tools used

Toolkit

The entire analysis was built inside Microsoft Excel using its Power Pivot data model, Pivot Tables, Pivot Charts, and DAX (Data Analysis Expressions). No helper formulas or manual calculations were used for the core metrics — every KPI displayed in the dashboards is driven by a DAX measure that recalculates dynamically as slicers and filters change.

Microsoft Excel Primary environment — all analysis, dashboards, and visualisation contained in a single workbook
Power Pivot Data model layer — loaded the raw dataset as a table, enabling DAX measures and relationships
DAX Measures Calculated all 7 core KPIs: Total Revenue, Total Orders, Returned Orders, Return Rate, Delayed Orders, Delay Rate, Avg Delivery Time
Pivot Tables Aggregated and sliced data across every analytical dimension — Region, Salesperson, Promotion, Customer Type, Product
Pivot Charts Visualised Pivot Table outputs as bar charts, combo charts, and line charts connected to slicers
Slicers & Timelines Interactive filters connected to all Pivot Tables and Charts, enabling cross-dashboard filtering by Region, Date, and Promotion
Conditional Formatting Applied to Pivot Table outputs to highlight top performers, outliers, and threshold breaches with colour scales and icon sets

03 data cleaning

Data Cleaning Process

The raw dataset (1,500 rows, 19 columns) was cleaned directly in Excel before being loaded into the Power Pivot data model. Cleaning the data at source ensures all Pivot Tables and DAX measures operate on accurate, consistent inputs without needing measure-level workarounds.

01
Date column conversion OrderDate and DeliveryDate columns were stored as Excel serial numbers (e.g. 44980). Converted to proper date format via Format Cells → Date. This is essential before loading into Power Pivot — the data model must recognise date columns as the Date data type to support timeline slicers and any future time intelligence DAX functions.
02
TotalPrice column audit TotalPrice was spot-checked against the expected logic of Quantity × UnitPrice × (1 − Discount) on a sample of rows. Minor floating-point rounding artifacts (e.g. 2290.4000000001) were confirmed as display issues only — Pivot Table aggregation handles these correctly. No corrections were needed.
03
Returned column verification The Returned column was checked to confirm it contained only binary values (0 = not returned, 1 = returned) with no nulls or unexpected entries. This column is the sole input for the Returned Orders and Return Rate DAX measures — any dirty values here would silently corrupt both metrics across all Pivot Tables.
04
DeliveryStatus column verification The DeliveryStatus column was filtered to confirm it contained exactly two values: "On Time" and "Delayed" with no spelling variants, extra spaces, or mixed casing. The Delayed Orders DAX measure filters on this exact string — any inconsistency would cause the measure to return a silent undercount.
05
Categorical field consistency check Region, Product, CustomerType, Promotion, PaymentMethod, and StoreLocation were each filtered and inspected for typos, trailing spaces, or casing inconsistencies. All values were consistent — no corrections required. Consistency here matters because Pivot Table row and column groupings are string-match based: a single "North " (with a trailing space) would appear as a separate group from "North".
06
Duplicate row check OrderID was checked for duplicates using the Remove Duplicates tool (Data tab). No duplicates were found. Duplicate rows in the data model would cause every aggregation — Total Revenue, Total Orders, and all derived measures — to overcount silently.
07
Blank cell scan The full dataset was scanned for blanks using Go To Special → Blanks. One unnamed trailing column was found and deleted. No blank values were present in any column used by a DAX measure. Blanks in measure inputs are handled by DAX's BLANK() behaviour — but known blanks should be removed or handled explicitly rather than left to DAX defaults.
08
DeliveryDays column formatting The DeliveryDays column (calculated as DeliveryDate minus OrderDate) was verified to be formatted as a whole Number. When date subtraction is performed in Excel, the result is sometimes stored as a Date serial rather than an integer — this would cause the Avg Delivery Time DAX measure to return an incorrect result. All values were confirmed as integers (1–10).
09
Data loaded into Power Pivot as a Table After cleaning, the dataset was formatted as an Excel Table (Ctrl+T, named SalesData) and then added to the Power Pivot data model via Data → Manage Data Model → Add to Data Model. Loading as a named Table (not a plain range) means the data model automatically expands to include new rows if the dataset is updated — no manual refresh of the range reference is needed.

04 dax measures

DAX Measures — What They Calculate & Why

All seven core KPIs were written as explicit DAX measures in the Power Pivot measure grid. Using explicit measures (rather than implicit Pivot Table aggregations) means each calculation is reusable across multiple Pivot Tables, produces consistent results regardless of the Pivot Table layout, and updates automatically when a slicer or filter changes.

M1 Total Revenue
DAX Power Pivot Measure Grid 
Total Revenue :=
  SUM( SalesData[TotalPrice] )

Why this measure

SUM over TotalPrice — not Quantity or UnitPrice — because TotalPrice already incorporates both quantity ordered and any discount applied, making it the realized revenue figure rather than a theoretical list price. Wrapping SUM in an explicit measure means it responds to every slicer filter (Region, Salesperson, Promotion) automatically, without needing to recreate the Pivot Table. Every revenue figure shown across all three dashboards is drawn from this single measure.

M2 Total Orders
DAX Power Pivot Measure Grid 
Total Orders :=
  COUNTROWS( SalesData )

Why this measure

COUNTROWS counts every row in the filtered table context — one row equals one order, so this is a clean and reliable order count. It is the denominator for both Return Rate and Delay Rate. If either of those measures is placed in a Pivot Table filtered by Region or Salesperson, Total Orders automatically returns the row count for that filtered subset — no additional filter arguments required.

M3 Returned Orders
DAX Power Pivot Measure Grid 
Returned Orders :=
  CALCULATE(
    COUNTROWS( SalesData ),
    SalesData[Returned] = 1
  )

Why this measure

CALCULATE modifies the filter context before evaluating COUNTROWS — here adding the condition Returned = 1 so only returned orders are counted. This is the correct DAX pattern for conditional counts. It respects every other filter already active (e.g. if the Pivot Table is grouped by Salesperson, it counts returned orders per salesperson; if filtered by Region via a slicer, it counts returns for that region only).

M4 Return Rate
DAX Power Pivot Measure Grid 
Return Rate :=
  DIVIDE(
    [Returned Orders],
    [Total Orders],
    0
  )

Why this measure

DIVIDE is used instead of a plain division operator ( / ) because it handles the zero-denominator case gracefully — if a Pivot Table row has zero orders (e.g. a region with no data in a filtered view), DIVIDE returns 0 instead of throwing a divide-by-zero error that would break the visual. The result is a decimal (e.g. 0.2481) formatted as a percentage in the Pivot Table value field settings. Normalising by Total Orders rather than using raw Returned Orders is critical: a salesperson with 76 returns from 270 orders (28.1%) is performing worse than one with 64 returns from 259 orders (24.7%), even though the second rep has fewer returns in absolute terms.

M5 Delayed Orders
DAX Power Pivot Measure Grid 
Delayed Orders :=
  CALCULATE(
    COUNTROWS( SalesData ),
    SalesData[DeliveryStatus] = "Delayed"
  )

Why this measure

Filters the table to rows where DeliveryStatus equals "Delayed" and counts them. Using the categorical DeliveryStatus column (rather than a numeric threshold on DeliveryDays) is more reliable in DAX — it relies on a value already encoded in the data rather than comparing a number against a dynamically computed average that would itself need to be a separate measure. This is why the DeliveryStatus column was verified for exact string consistency during data cleaning.

M6 Delay Rate
DAX Power Pivot Measure Grid 
Delay Rate :=
  DIVIDE(
    [Delayed Orders],
    [Total Orders],
    0
  )

Why this measure

Same DIVIDE pattern as Return Rate — Delayed Orders divided by Total Orders, returning 0 if the denominator is zero. Rate (not raw count) is the right metric here because regions have different order volumes. The North region having 163 delayed orders out of 309 (52.75%) is a fundamentally different problem from the East region having 138 delays out of 311 (44.37%), even though the raw counts look similar. Only the rate reveals the true severity.

M7 Avg Delivery Time
DAX Power Pivot Measure Grid 
Avg Delivery Time :=
  AVERAGE( SalesData[DeliveryDays] )

Why this measure

AVERAGE over the DeliveryDays column gives the mean delivery duration across all orders in the current filter context. This is appropriate here because DeliveryDays is a bounded integer (1–10 days) with no extreme outliers — the bounded range means the mean is not distorted by a handful of unusually long deliveries the way an unbounded distribution could be. The measure filters automatically by Region when placed in a Pivot Table with Region as the row field, enabling per-region average delivery time without any additional DAX filter arguments.

// how the measures connect

M2 (Total Orders) is the shared denominator for both M4 (Return Rate) and M6 (Delay Rate). This means all three measures are always consistent — if Total Orders changes (e.g. due to a slicer filter), both rates update simultaneously using the same denominator. M3 (Returned Orders) feeds M4; M5 (Delayed Orders) feeds M6. M1 (Total Revenue) and M7 (Avg Delivery Time) are independent. Together these seven measures power every KPI card, every Pivot Chart, and every table across all three dashboards.

07 recommendations

Recommendations

Based on the Pivot Table outputs and DAX measure results across all four questions, the following recommendations are offered to improve revenue performance, reduce return costs, and address delivery inefficiencies.

// action items
  • Prioritise FREESHIP in future campaigns. FREESHIP is the only promotion delivering a meaningful positive revenue lift (+$51.47 per order) and the highest total order volume (419). Future budget should weight free shipping over percentage discount promotions, particularly for Wholesale customers whose order values can absorb the shipping subsidy.
  • Discontinue or restructure WINTER15. WINTER15 is the only promotion producing a negative revenue lift (−$13.26 per order vs. the no-promotion baseline). Customers spend less per order under WINTER15 than without any promotion at all — it is actively eroding revenue. A review of targeting, timing, or product-category scope is needed before running it again.
  • Audit North region logistics. At 52.75% delayed — the worst of any region — North's supply chain needs a targeted operational review. This is especially urgent given that North is simultaneously the top revenue region. A delay problem at the top of the revenue ladder carries the highest retention risk.
  • Investigate and coach Carlos on return reduction. Carlos has both the highest return rate (28.15%) and the most orders (270), producing 76 returns — the highest raw return count of any rep. A targeted analysis using the Pivot Table filtered to Carlos's orders (segmented by Product and Region) would identify which specific combination drives his disproportionate returns.
  • Use Alice as the team benchmark. Alice is the only rep who ranks in the top two for both revenue (#2) and return rate quality (#2) simultaneously. Documenting and sharing her approach — which products she prioritises, which customer segments she focuses on, how she matches product to customer — is the most cost-effective quality improvement lever available.
  • Investigate Central's return rate separately from delivery. Central has the best delivery performance (42.52% delay rate, 5.88 day avg) but the highest return rate (28.57%). Since the delay-return correlation is weak, Central's returns are driven by something other than logistics — likely product quality, order accuracy, or customer expectation mismatch. A dedicated Pivot Table segmented by Product and CustomerType within Central would surface the pattern.
